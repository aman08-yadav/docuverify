# DocuVerify Deployment Checklist

This guide is for the current React/Vite + Express + MongoDB version of DocuVerify.

## Hosting choices

- **Frontend:** Vercel, project root is the repository root (`./`) because the root `vercel.json` runs npm workspaces and publishes `client/dist`
- **API:** Render Blueprint from `render.yaml`
- **Database / private uploaded documents:** MongoDB Atlas Free cluster for a demo
- **Source / CI:** GitHub repository, with the included Actions workflow

The Render Blueprint is set to the **Free** web-service plan to avoid silently selecting a paid service. Free instances can sleep, have limited CPU/RAM, and are intended for demos rather than production workloads. OCR can be slow or exceed their resource limits. Review provider pricing before upgrading any resource.

## 1. Push the source to GitHub

On Windows, the easiest route is to extract the ZIP, open PowerShell in the extracted `docuverify` folder, and run:

```powershell
.\DEPLOY-WINDOWS.ps1
```

The helper uses GitHub CLI (`gh`) and normal browser authorization. If GitHub CLI is missing, install it with `winget install --id GitHub.cli -e`, reopen PowerShell, and run the script again. The helper creates a **private** `docuverify` repository under the account authenticated in GitHub CLI and pushes the current source. It then opens the Atlas, Render, and Vercel dashboards for the remaining service setup. It does not claim the hosted app is live just because the Git push succeeds.

Manual alternative: create an empty repository (do not pre-add a README or `.gitignore`) and use `git init -b main`, `git add .`, `git commit -m "Initial DocuVerify deployment"`, `git remote add origin https://github.com/YOUR-USERNAME/docuverify.git`, and `git push -u origin main` from this folder.

Do not put a personal access token or password into commands or share it in chat. The repository root must contain `package.json`, `render.yaml`, `vercel.json`, `client/`, and `server/`.

Before pushing, check that no real `.env` file, password, database URI, API token, uploaded document, or `node_modules` directory is included. `.gitignore` already excludes common secret/local files; keep all actual credentials in provider environment settings only.

The root package uses npm workspaces, so install dependencies from the repository root, not from `client/` or `server/` separately.

## 2. Create the Atlas database

1. Create a small Free cluster in MongoDB Atlas for this demo.
2. Create a dedicated database user with a strong, unique password.
3. Configure Network Access to allow the Render service's outbound IP ranges shown in Render's service settings. Avoid opening database access to the entire internet unless you understand and intentionally accept that risk.
4. Copy the `mongodb+srv://...` connection string, set the database name to `docuverify`, and store it as the Render `MONGODB_URI` secret. URL-encode special characters in the username/password.

Do not paste this URI into chat, commit it, or put it in a `VITE_` variable. Uploaded files are stored in MongoDB GridFS.

## 3. Deploy the backend on Render

1. In Render, create a **Blueprint** using the GitHub `docuverify` repository. Render should detect `render.yaml` at the repository root.
2. Review the Blueprint before applying it; leave the plan on `free` unless you intentionally choose a paid plan.
3. Provide `MONGODB_URI`. `JWT_SECRET` is generated by the Blueprint. `CLIENT_ORIGIN` can be a temporary placeholder until Vercel creates the final frontend URL; update it in Step 4.
4. Wait for the first deploy. The service's health route is `/api/health`.
5. Copy the actual public Render service URL from the dashboard; do not assume it matches an example URL.

Expected health response: HTTP 200 with `success: true` after the database connects. HTTP 503 indicates the service cannot reach MongoDB or the database connection is not healthy.

## 4. Deploy the frontend on Vercel

1. Import the same GitHub repository as a new Vercel project.
2. Keep **Root Directory** at the repository root (`./`) so npm workspaces are installed from the root package.
3. Select the Vite framework preset. The included root `vercel.json` defines `npm install`, `npm run build`, and output directory `client/dist`.
4. Add the environment variable `VITE_API_URL` with the full API base URL ending in `/api`, for example `https://YOUR-ACTUAL-RENDER-HOST.onrender.com/api`.
5. Deploy and copy the final production frontend origin, for example `https://your-project.vercel.app` (no trailing slash).
6. Return to Render and set `CLIENT_ORIGIN` to that exact origin, including `https://` and no trailing slash. Redeploy/restart the backend after saving it.

The app uses HTTP-only cookies and CSRF protection. The frontend/API pair may be subject to third-party-cookie restrictions because Vercel and Render use different host domains. Test login on the browsers/devices you care about. For a more reliable production setup, use custom frontend/API domains under the same registrable domain and configure cookie settings for that arrangement.

## 5. Seed demo scholarship criteria

The sample scholarship programs are synthetic demonstration rules, not official scheme data. Run the seed script from a trusted local computer with Node 24/npm 10+ and a temporary `server/.env` containing the Atlas `MONGODB_URI` and a strong `JWT_SECRET`:

```bash
npm install
npm run seed
```

Never use real student records just to test the demo.

## 6. Create an administrator

From a trusted local computer, create `server/.env` using `server/.env.example`. Set the same Atlas `MONGODB_URI`, a strong `JWT_SECRET`, and a unique `ADMIN_EMAIL` plus a strong `ADMIN_PASSWORD` of at least 16 characters. Then run:

```bash
npm install
npm run create-admin
```

Remove the temporary local environment file when done and never commit it. Registration from the public site always creates a student account; it cannot grant admin access by itself.

## 7. Smoke-test before sharing the link

- Open the Vercel frontend and confirm the landing page loads.
- Register a demo student, log in, refresh the page, and log out/in again.
- Upload only `server/src/tests/fixtures/marksheet-demo.png` or another synthetic test file.
- Confirm OCR status changes, fields/evidence render, and document history is scoped to that account.
- Run a sample scholarship assessment and inspect its explanations.
- Confirm a student account cannot open admin routes.
- Check Render logs, Vercel deployment logs, and `/api/health` if a request fails.
